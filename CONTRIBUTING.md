# Contributing

Thanks for your interest in `apicalls`. Bug reports, missed or false calls, new SDK registries,
new languages and documentation fixes are all welcome.

## Reporting a missed or wrong call

Open an issue with a **minimal snippet** (TypeScript or Python) that reproduces it, the command you
ran, and what you expected to see. A snippet of a few lines is far more useful than a link to a
large repository. Never paste code, hosts or credentials from a private codebase: rewrite the
pattern with invented names.

## Development setup

Requires Node.js 20+ and [pnpm](https://pnpm.io).

```sh
pnpm install
pnpm dev scan tests/fixtures/fetch   # run the CLI from source
pnpm dev scan tests/fixtures/polyglot  # TypeScript and Python in one repository
pnpm test                            # vitest: fixture snapshots, integration and unit tests
pnpm test:e2e                        # builds dist/ and runs the CLI as a subprocess
pnpm lint                            # type-aware eslint, zero warnings allowed
pnpm typecheck
pnpm build                           # tsup -> dist/
```

A Husky pre-commit hook runs lint-staged, the type checker and the tests. CI also runs the
end-to-end suite on Node.js 20, 22 and 24 and `pnpm audit --prod --audit-level high`.

## Tests

- Every detection or resolution change needs a fixture. Add a file under the relevant
  `tests/fixtures/<group>/` folder (`tests/fixtures/python/<group>/` for Python) and assert on it
  in `tests/fixtures.test.ts` (or `tests/python.test.ts`) with `at(report, "<file>", <line>)`.
- Negative cases (code that must **not** be reported) go in `tests/fixtures/negatives/`.
- Fixtures are written from scratch with invented names and only public provider hosts.
- Regression fixtures: a directory under `tests/fixtures/` with an `expected.json` lists the
  calls a scan must find (`file`, `line`, `provider`). An empty `calls` list marks a negative
  fixture; `orUnfollowed` accepts a `diagnostics.unfollowed` entry instead of a call; `todo`
  (an issue URL) parks a fixture whose feature is not built yet. `tests/recall.test.ts` scans
  them all, snapshots their calls and prints `recall 1.00, false calls 0`. It fails when recall
  drops below `tests/recall-baseline.json` or a negative fixture gives a call; raise the
  baseline when recall improves.
- Snapshots are part of the review. After an intended change, update them with
  `pnpm vitest run -u` and check the diff.
- CLI behavior (options, output formats, exit codes) and anything about untrusted input
  belongs in `tests/e2e/`: those tests spawn `dist/cli.js` and build throwaway repositories
  with `tempRepo()`. `APICALLS_E2E_CLI=/path/to/cli.js` runs them against another build.

## Adding an SDK registry

### TypeScript

1. Create `src/detect/registry/<sdk>.json`:

   ```json
   {
     "package": "openai",
     "provider": "openai",
     "host": "api.openai.com",
     "auth": "bearer",
     "generatedFrom": "manual",
     "instance": { "names": ["default", "OpenAI"] },
     "methods": {
       "chat.completions.create": { "method": "POST", "path": "/v1/chat/completions", "bodyArg": 0 },
       "files.retrieve": { "method": "GET", "path": "/v1/files/{file_id}", "pathArgs": [0] }
     }
   }
   ```

   Each key in `methods` is the member chain after the client instance. `bodyArg`, `queryArg`
   and `pathArgs` give the argument positions; `pathFromBody` takes path parameters from body
   properties; `encoding` sets the body encoding (`form`, `multipart` or `raw`; JSON otherwise). A
   method can also set its own `host` and `auth`, read its body from a property of an argument
   (`bodyProp`), and name where each path placeholder comes from in `params`: `arg:N`,
   `instance:N` (the builder it is called on, `from(table)`) or `ref:N` (a Firebase reference).
   With `inlinePathLiterals`, literal values are written into the path; `instance.urlArg` names
   the constructor argument that holds the base URL. An alias ending in `/*` covers a whole
   scope (`@sentry/*`). `urlArg` can point into an options object (`"0.baseURL"`), `basePath`
   is the path prefix that a code-given base URL replaces (`/v1` for OpenAI), `urlFromFile`
   takes the base URL from a transport built in the same file (MCP), and `fn:N` reads a Convex
   function reference. AI SDK model factories live in
   [`src/detect/registry/ai-sdk.json`](src/detect/registry/ai-sdk.json). See `MethodSpec` and `RegistryEntry` in [`src/types.ts`](src/types.ts)
   for every field.
2. Register it in `defaultRegistry()` in [`src/detect/registry/index.ts`](src/detect/registry/index.ts).
3. Add a fixture in `tests/fixtures/sdk/`. If detection relies on the package's types, add the
   SDK as a dev dependency.

`pnpm gen:registry stripe|openai` regenerates those two registries from the vendor OpenAPI
specs (network access required). Review the diff before committing.

### Python

Python registries live in `src/lang/python/registry/` and use the same format, plus:

```json
{
  "package": "openai",
  "imports": ["openai"],
  "provider": "openai",
  "host": "api.openai.com",
  "auth": "bearer",
  "generatedFrom": "manual (checked against openai-python 1.x)",
  "instance": { "names": ["OpenAI", "AsyncOpenAI"], "urlArg": { "OpenAI": "kw:base_url" } },
  "basePath": "/v1",
  "builders": ["with_raw_response"],
  "methods": {
    "chat.completions.create": { "method": "POST", "path": "/v1/chat/completions", "bodyKwargs": true },
    "files.retrieve": { "method": "GET", "path": "/v1/files/{file_id}", "params": { "file_id": "arg:0" } }
  }
}
```

`package` is the PyPI distribution a requirements file declares and `imports` the dotted modules the
SDK is imported from. Keys are the chain after the client (`client.chat.completions.create`), or after
the import root for module-level APIs (`stripe.Customer.create` is `Customer.create`). `bodyKwargs`
makes the keyword arguments the body, `bodyKw` names one keyword argument holding it, `queryKwargs`
reads the query from keyword arguments. Path parameters also accept `kw:<name>`, `seg:<call>:<N>`
(argument N of a named call in the chain, `services(sid)`) and `chain:<a>,<b>` (Firestore references);
`arg:N` matches the keyword argument named like the placeholder too. `builders` are calls that only
narrow a request (`collection`, `document`). See `IrRegistryEntry` in
[`src/lang/ir/language.ts`](src/lang/ir/language.ts) for every field.

1. Add the file and import it in [`src/lang/python/index.ts`](src/lang/python/index.ts) (`PYTHON_REGISTRY`).
2. List the distribution under the provider's `packages.pypi` in `providers.json`, and its import
   name in [`src/lang/python/modules.json`](src/lang/python/modules.json) when it is not the name with
   `_` for `-`. `tests/unit/ir-registries.test.ts` checks both.
3. Add a fixture in `tests/fixtures/python/sdk/` and run `pnpm gen:support`.

The Python Stripe registry is derived from the TypeScript one: run `pnpm gen:stripe-ports` after
`pnpm gen:registry stripe`.

## Adding a language

Languages other than TypeScript are parsed with tree-sitter and lowered into a small model that a
shared engine detects and resolves. [docs/languages.md](docs/languages.md) explains the architecture
and has the checklist; `src/lang/python/` is the reference implementation.

## Changing the report format

The report is a contract other tools read. Its source is [`src/report/schema.ts`](src/report/schema.ts):

1. Change the zod schema, with a `describe` for every new field.
2. Run `pnpm gen:schema` to regenerate [`schema/report.v1.json`](schema/report.v1.json);
   `tests/schema.test.ts` fails until you do.
3. Bump `SCHEMA_VERSION`: the minor for a new field or enum value, the major for anything that
   can break a reader (a removed, renamed or retyped field). A major also moves the schema to
   `report.v<major>.json` and updates `SCHEMA_URL`.
4. Update the YAML example in the README's [Output format](README.md#output-format) section.

## Code style

- TypeScript, ESM, strict mode.
- ESLint enforces at most 300 lines per file and 50 lines per function. Split code rather than
  disabling the rule.
- Keep the scanner static: no network calls, no code execution, no AI.
- Detection and resolution are per language; everything after a `Call` is built (provider,
  confidence, examples, specs, redaction, diagnostics, coverage) is shared. Keep it that way.
- Treat everything read from a scanned repository as hostile: print it through `printable()`,
  read config files and manifests through `readConfigFile()`, and add a case to
  `tests/e2e/security.e2e.test.ts` when a new output can carry it.

## Pull requests

1. Fork the repository and branch from `main`.
2. Keep each pull request to one topic, with tests.
3. Make sure `pnpm lint`, `pnpm typecheck`, `pnpm test` and `pnpm test:e2e` pass. CI runs the
   same checks. If a registry or `providers.json` changed, run `pnpm gen:support` (a test fails
   when `docs/sdk-support.md` is stale).
4. Explain *why* in the description, and include before/after output when the report changes.
